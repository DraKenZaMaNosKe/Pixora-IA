## What changed (developer changelog)

### Root cause finally found

After 7+ hours of debugging on Samsung RF8X903KZ3K, Eduardo's intuition
nailed it: **regression from v1.7.5** (commit `d44ad04`). Two things had
silently changed since the "ads worked fine" era:

1. **Alternating skip removed (v1.7.5, 2026-05-05)** — went from showing
   ads on odd action counts (1st, 3rd, 5th) to ALWAYS showing. Doubled
   user exposure to playable creatives.

2. **google_mobile_ads upgraded v5 → v8 (commit 2361771, April 2026)** —
   v8 SDK serves new ad formats more aggressively (playables, rewarded
   video) which weren't common in v5. Those creatives need 200-400 MB
   GPU memory to render their interactive mini-game; on Samsung mid-range
   devices they stutter, freeze the screen, and sometimes ANR the app.

Combined effect: every other wallpaper apply triggered a heavy playable
creative on a memory-pressed device. User saw "se traba el ad" pattern.

### The actual fix (3 lines)

```dart
// 1. Restore alternating skip (lib/core/services/ad_service.dart)
final shouldShow = _actionCount.isOdd;
if (!shouldShow) {
  onAdDismissed();  // skip silently, wallpaper applies
  return;
}

// 2. Filter heavy ad formats via SDK (no AdMob console change needed)
await MobileAds.instance.updateRequestConfiguration(
  RequestConfiguration(maxAdContentRating: MaxAdContentRating.g),
);
```

`MaxAdContentRating.g` excludes Teen/Mature creatives. Game playables
(Hill Climb, Royal Match, Royal Kingdom) are usually rated T or higher,
so AdMob no longer serves them to Pixora. Free users see lightweight
static interstitials (retail, finance, lifestyle) which fit comfortably
within the device's GPU budget.

### Memory baseline improvements (parallel work)

Several improvements made during the debugging session that lowered
Pixora's memory baseline from 1 GB → 529 MB on idle:

- `_CategoryRows`: Column → ListView.builder lazy with cacheExtent 200
- `WallpaperCarouselRow`: addAutomaticKeepAlives = false (offscreen
  carousels dispose properly)
- `CachedWallpaperImage` default `maxDecodedWidth`: 640 → 320 logical px
- `main.dart`: Skia GPU resource cache capped at 64 MB via
  `SystemChannels.skia.invokeMethod('Skia.setResourceCacheMaxBytes')`
  in `addPostFrameCallback` (must be after the engine shell is ready)

These reduce memory pressure across the app, not just during ads.

### Side fixes left in place

- 3-minute watchdog timer in `showInterstitialAd` as last-resort rescue
  if AdMob never emits dismiss/fail callback (some abusive creatives
  never close on their own).
- Image cache temporary clamp to 0 + clear before show (frees Java heap
  bitmaps; doesn't fix GPU but doesn't hurt).

### Files touched

- `lib/core/services/ad_service.dart` — alternating restored, MaxAdContentRating
- `lib/main.dart` — Skia GPU cache cap (postFrameCallback)
- `lib/widgets/cached_wallpaper_image.dart` — decode width 640→320
- `lib/features/wallpapers/presentation/pages/wallpapers_page.dart` — lazy CategoryRows
- `lib/features/wallpapers/presentation/widgets/wallpaper_carousel_row.dart` —
  dispose offscreen items
- `pubspec.yaml` — bump 1.7.9+51 → 1.7.10+53

## Lessons learned

1. **Trust user historical context** — when Eduardo said "antes funcionaba
   bien", that was a regression flag. Two specific commits broke ads:
   d44ad04 and 2361771. Both were valid changes individually but
   combined produced a hidden bug.

2. **AdMob v8 vs v5 — major behavior shift** — v8 SDK is more aggressive
   serving playable formats. Apps targeting mid-range hardware should
   pin `maxAdContentRating` to G or PG to avoid heavy creatives.

3. **Memory pressure is multi-source** — Skia GPU cache, image cache,
   `:wallpaper` process, and offscreen widget tree all contribute.
   Capping each individually is more effective than nuking one.

4. **Nuclear approaches (kill :wallpaper, swap root) cause new bugs** —
   in this case ANRs. Surgical fixes (alternating + content rating)
   are safer.
